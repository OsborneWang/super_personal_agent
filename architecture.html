1 · sa 与 pi 的区别

同一个 pi 二进制，两种身份。sa 是通过包装器以 SA_MODE=1 启动的 Router 会话，工具被收窄为只有 file_ticket；pi 是纯净的编码助手，扩展根本不加载。

2 · 总体拓扑

一个全局 agentd 常驻服务；任意多个项目目录都可以作为 Router 的发起地。任务归属 = 发起时的目录（不可变）， Worker 就在该项目的物理目录里干活。全局只存运行记录（账本 / socket / 全局配置）。

3 · 一个任务的完整生命周期

实线 = 请求 / 写入；虚线 = 返回 / 通知。图上同时画出三条真实会走到的支线：需要人回答、拆子任务、Worker 死亡重试。

4 · 状态机（闭集，迁移必须查表）

区分 pending（等依赖/尚未就绪）、ready（等资源）与 running（在跑）——这是回答"为什么它没在跑"的前提。 closed 是终态：到达后除资源释放事件外，任何事件都会被拒绝。

5 · 核心实体与账本

六个实体就是内核的最小完备集——再少就不通用了。所有变化都表达为账本事件，状态是账本的投影。
Task

任务（可递归的树）

任意深度，叶子才是执行单元。depth / max_depth 限制最多三层。

  • parent_id 形成任务树
  • 含 goal / acceptance / context
Attempt

一次有界执行

绑定 session_id 与 worker_pid。失败重试用同一 session-id，继承上下文。

  • attempt 计数受 max_attempts 限制
  • 进程组隔离（setpgid）
Resource

资源租约

(kind, key, mode)，内核只保证"同 key 同刻一个独占持有者"，不关心 key 是什么。

  • key 自动加项目命名空间
  • 冲突则排队等待
Artifact

产物 / 证据

trace.jsonl（Worker 完整事件流）与 result.md（最终输出）。删掉不影响正确性。

  • 放在项目目录里
  • 供审计与复盘
Gate

人工门禁

需要人或授权方裁决的点：入档确认、need_input、max_depth 预警、waiting 超时。

  • 入档确认在工具内部弹出
  • 模型无法伪造
Ledger

账本（唯一真相）

append-only JSONL，seq 全局单调。状态只由 agentd 写，Worker 只能申报意图。

  • 单 goroutine 写入
  • 可 grep、可回放、可自愈
账本事件（闭集）含义
ticket.admitted人工确认后入档（草稿 → 正式任务）
state.changed状态迁移，只由 agentd 写，带 reason 与触发者
run.claimed / run.ended一次执行的开始与结束（带模型、结局、用量）
question.asked / answer.givenWorker 提问与人回答（waiting_user 的载体）
resource.allocated / resource.released资源租约获取与释放
notification.sent通知记录（可统计"一天被打扰几次"）
reconcile.applied启动自愈做了哪些修复

6 · 三层约束与配置分层

系统管"规则必须在场 + 结果必须交代"，不管"规则是什么"。所以换项目不必改内核——改配置文件即可。 优先级：项目配置 > 全局配置；规则是拼接而非覆盖。
L1 · 通用内核

系统强制

所有项目共有，写在代码里，无法绕过。

  • goal 非空 / acceptance ≥ 1 / context 自包含
  • 最多三层递归
  • 同 key 资源互斥
  • closed 是终态
L2 · 项目规则

注入，不解析

项目自己的约束（禁主库、必须用某脚本、禁止改某目录…），以文件形式注入 Worker 的 system prompt。

  • 来自 <项目>/.agent/config.yaml 的 rules
  • 不同项目互不污染
L3 · 单任务约束

随票下发

只对这张票生效的约束：不许碰前端、不许 commit、必须写报告…

  • 写在 ticket 的 constraints 里
  • Worker 需在报告中逐条交代
配置项全局 ~/.agent/config.yaml项目 <项目>/.agent/config.yaml合并方式
model.worker兜底默认覆盖项目优先
model.router兜底默认覆盖项目优先
rules全局规则项目规则拼接（两者都生效）
waiting_timeout_minutes兜底 30覆盖项目优先
max_attempts兜底 3覆盖项目优先

7 · 资源互斥与递归

左：两个项目使用同名资源，因为 key 自动加项目命名空间，互不冲突、可并行。 右：同一项目内同名资源则真正互斥，后来的排队等待。

8 · CLI 命令面

日常只需一个入口 sa。底层二进制是 agent，sa 是它的包装 + Router 启动器。

9 · 已实现并验证的能力

每一条都对应一次真实运行验证，不是纸面承诺。

✓ 崩溃自愈

kill -9 agentd 后：systemd 自动拉起 → 重放账本 → 发现孤儿 Worker → 用同 session-id 重试，不丢上下文，且不会出现死亡检测死循环。

✓ 状态机强制

状态迁移查表校验，非法迁移被拒绝；closed 之后除资源释放外任何事件都不接受。

✓ 真实 Worker 干活

实测：联网 curl 多个 API 交叉验证后汇总成表、写文件、跑命令、逐条自检验收标准并输出控制标记。

✓ need_input 闭环

Worker 停下提问 → 通知你 → sa answer → 同 session-id 恢复继续。Worker 会拒绝编造，遇到无法满足的前提如实报告。

✓ 递归子任务

父 Worker 用 create_subtask 拆子任务 → 父等子 → 子结果回填后父用同 session-id 恢复整合。

✓ 资源互斥

同项目同 key 排队、释放后自动接续；跨项目自动命名空间，可并行。

✓ 多项目隔离

一个 daemon，多个项目目录；Worker 在各自项目目录运行，能直接读写项目文件，规则与配置互不污染。

✓ 可审计

账本 append-only、零截断行；任意状态都能从事件流复盘。trace 与 result 作为证据留在项目目录。
